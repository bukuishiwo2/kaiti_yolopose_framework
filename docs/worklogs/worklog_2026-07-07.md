### 2. 空间状态层从未知探索假设收回到已知环境假设

今日运行发现，直接把 `/global_costmap/costmap` 用作规划资源判定时，会把 `corridor_H`、`charger_D` 等区域误判为 `blocked/occupied`，导致 MILP 无解。

已作调整：

- `planning_stack.yaml` 中 `spatial_state_node.costmap_topic` 改为 `/map`，优先使用已知地图而非膨胀后的全局代价图。
- `configs/planner_regions.yaml` 收紧 `corridor_H / charger_D / event_zone_B / supply_point_S` 区域边界，避免区域框直接压到墙体边缘。
- 将区域配置中的 `unknown_as_occupied` 调整为 `false`，符合“已知环境任务规划”的毕业设计假设。
- `spatial_state.py` 中通道宽度估计由“最小整行空闲宽度”改为“每条扫描线最长连续自由段，并取非零中位数”，避免 region 擦到墙边就把 `min_width` 压成 0。
- `spatial_state.py` 中在线资源状态的 `available_from` 改为规划相对时间，不再把 ROS wall time 直接传入 MILP。

运行结果已经从早期的：

- `corridor_H -> blocked`
- `solver_status -> error`

推进到：

- `corridor_H -> free`
- `charger_D -> available`
- `event_zone_B -> reachable`
- `supply_point_S -> reachable`
- `solver_status -> Optimal`

### 3. MILP 在线计划发布修复

今日发现 `/planning/plan` 在线发布时曾出现极大的绝对时间戳，例如 `1783431500`，导致任务顺序漂移和执行器反复刷新计划。

已作调整：

- `milp_planner_node.py` 对来自空间状态的 `available_from` 做相对时间归一。
- 若空间状态仍带有旧式绝对时间戳，planner node 会回退使用 `wait_time`，避免巨大时间进入 MILP。
- 静态 MILP 验证仍保持预期结果：
  - `R2: T2@C [0,20]`
  - `R2: T4@B [53,78]`

单机器人在线执行中，`T4` 会被执行器展开为：

- `S`：取货点
- `B`：任务点

因此当前单车演示下，预期访问顺序应为：

```text
T2@C -> T4 pickup@S -> T4 task@B
```

### 5. 执行中计划刷新问题修复

运行中发现在线 planner 周期性重算会改变 `R2` 的任务顺序，导致小车重复访问右上角或反复接收更新计划。

已作调整：

- `milp_plan_executor_node.py` 新增 `allow_plan_refresh_during_execution` 参数。
- 当前 demo 默认 `false`。
- 一旦执行器加载第一份计划，后续周期性计划更新不会重置执行队列。
- 后续真正做事件触发完整重规划或局部修复时，再显式打开或替换为事件触发策略。

这符合当前阶段目标：

- 先验证 `MILP -> Nav2` 最小执行闭环。
- 不在 demo 阶段让周期性 planner 刷新扰乱任务访问顺序。

### 6. TF 与 costmap 启动问题检查

今日多次观察到：

- 手动给初始点/目标点后，小车有时不动。
- 日志出现 `Robot is out of bounds of the costmap` 或 sensor origin out of map bounds。
- 小幅键盘转动后，问题消失并开始运动。

在线检查结论：

- `/odom -> base_link` 可用。
- `map -> base_link` 曾出现不稳定或不可查询。
- 这会导致 Nav2 在 map frame 中一开始无法稳定判断机器人是否落在 costmap 内。

已作调整：

- `kaiti_house_turtlebot4_rtabmap.launch.py` 和 `phase4a_turtlebot4_rtabmap.launch.py` 显式传入 `odom_frame_id=odom`。
- 显式传入 `publish_tf_map=true`，确保 RTAB-Map 发布 `map -> odom`。
- `milp_plan_executor_node.py` 新增 `require_tf_ready` 参数。
- 执行器发 Nav2 goal 前会检查 `map -> base_link` TF。
- 若 TF 不可用，状态会保持：

```text
holding / tf_unavailable:map->base_link
```

这样可以避免 TF 未就绪时过早下发目标，触发 costmap out of bounds。

## 结构性结论

- 今日已证明规划层主链路可以从 `blocked/error` 推进到 `Optimal/executing`。
- 当前问题已经从“规划层不可行”转移为“Nav2 执行层和 TF/costmap 初始化稳定性”。
- 毕业设计主线应保持在已知环境下的任务规划、资源状态估计和在线修复，不应把未知环境自主探索作为必要目标。
- `m-explore-ros2` 可作为后续工程增强项，但不应成为当前毕业设计主线前置依赖。
- 当前 demo 中必须冻结执行期计划，避免周期性 MILP 重算破坏访问顺序。
- 后续真正做动态扰动时，应由事件触发完整重规划或局部修复，而不是无条件周期性刷新执行队列。
