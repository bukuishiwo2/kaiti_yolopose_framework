# Clinic 研究实验与任务规划说明

本手册服务于“事件感知 → 任务生成 → 多智能体协同规划 → 执行反馈”主线。展示实验的研究内容贡献和证据等级必须分开填写，Clinic医院场景只承担验证作用。当前最优先的研究问题是新事件到达时，具备不同能力的机器人能否在已有承诺、任务依赖和共享资源约束下完成在线协同。

这份说明给网页展示和论文写作使用。网页把原始运行记录保留为审计证据，但默认只显示“研究实验目录”中的核心运行；工程探针、启动联调和失败的开发轮次仍保留在“全部历史记录”，不会被删除。

## 实验名称怎么读

展示名称使用“内容｜问题｜场景｜方法｜证据”。例如“内容1-2-3｜真实跌倒正例闭环｜fall-01视频｜核验→监护→取送”直接说明它验证哪三项研究内容、输入是什么、任务如何展开、证据来自哪里。原始 `run_id`、`C0_r3_W2` 等字段继续显示在审计模式和来源详情中。

任务 ID 中的 `C`、`r`、`W` 是历史任务生成器字段：`C` 是周期索引，`r` 是名义任务通道，`W` 是站次。它们不是前端标签，也不表示实际机器人或地图节点。实际执行机器人必须读取运行记录中的 `robot` 或计划版本的 `owners`。

## 一次任务从哪里产生

常态任务由 `tools/dense_tasks.py::cycle_tasks` 按周期、名义通道和站次生成。它先产生任务定义，再由规划器读取机器人能力、预计可用时间、空间锚点、资源和任务依赖。视觉事件任务不由执行器直接写入：真实模型产生稳定候选后，`src/kaiti_task_sim/clinic_visual.py` 的 event-task/v1 编译器先生成核验任务；只有收到带来源的核验结果，才会释放监护、取货和交付任务。

## 任务节点从哪里来

当前 Clinic 运行首先使用场景配置和冻结任务定义中的服务锚点，例如 A 区的 V1、M1、H1 和取货点 G1，并为资源阶段保存 entry/clear 节点。它们是预先配置的地图服务位置；现有证据不足以证明这些坐标来自真实医院测绘，也不是从任意一帧视频在线估计出来的随机三维目标。网页把“静态注册位置”“人体视频源注册区域”“传感器估计位置”和“实际 Nav2 目标”分开显示。

因此当前系统确实是“机器人先在已知地图坐标中定位，再去已知服务点移动”。机器人从Gazebo/定位来源取得自身位姿；任务点来自预先配置的Clinic地图节点。跌倒位置随机时，当前真实视频实验的 `event_xy` 使用 `video_source_registered` 区域登记：语义事件按区域A映射到核验/监护/交付服务点，任务目标因事件区域而改变，但不是从随机人体像素在线计算出的精确落地点。当前正例实际闭环只完成A区；B区注册已做，但其完整取货路径资格未通过，不能说双区均已正式可执行。`sensor_estimated` 的RGB-D/TF/CameraInfo接口仍保留，但尚未完成独立三维定位实验，不能把 `video_source_registered` 写成传感器估计。

## 旅行代价如何计算

MILP 读取每个冻结问题中的 `travel_times` 矩阵。当前代表场景的路径先验按语义配置空间格点路径长度除以约 `0.22 m/s`，并为每段加入约 `12 s` 姿态/ACK先验；任务阶段转移使用 `上一任务驶离时间 + travel_times[上一清空点][下一入口] + 下一任务接近时间`。这只是模型时间先验，不保证实际耗时上界。它不是浏览器直线距离，不是未来 Nav2 折线，也不是动态障碍预测。Clinic确实使用地图、Nav2路径查询、真实导航与服务阶段资格检查，因而纳入了模拟环境中的可达性和占用条件；但这不能等同于真实医院测绘、多机动态交通的完整环境模型。Nav2 的 ComputePathToPose、FollowPath 和实际位姿采样是执行证据，不能反向改写 MILP 代价。

## 任务之间如何建立约束

约束来源分开保存：

- 依赖字段形成严格前置，例如核验完成后才可释放后续任务，取货完成后才可交付。
- 能力和空间资格限制谁可以执行任务。
- 时间窗、预计可用时间和执行状态限制何时能插入。
- G1 等共享资源使用完整 entry/service/clear 区间互斥。
- 监护覆盖是持续运行守卫，不等同于一条普通完成前置边。
- pickup/deliver 的同车和携货所有者约束保护物资身份。
- 已派发、正在执行、活动监护和携货任务形成执行承诺，不能被普通重规划随意释放。

## 局部重规划究竟改变什么

床阻挡或资源/状态变化使旧计划约束失效后，局部修复器计算受影响任务的影响闭包，只释放这部分可调整后缀；活动监护、携货和已接受硬承诺作为保护前缀继续保留。它改变的是可优化任务的集合、任务顺序和时间安排，必要时才改变未承诺任务归属；它不等于“释放了多少任务就改派了多少机器人”。当前 `unified_bed_local_r1` 的三次更新来自同一次持续阻挡，均释放 10/11 个后缀任务，但实际改派为 0，且 CBC 达到时间上限。因此它能证明受约束恢复功能，不能单独证明局部算法普遍优于全量重规划。

## 三个研究内容是否打通

在 `positive_02` 这一受控 A 区样本中，链路已打通到有限功能闭环：真实 YOLO Pose/LSTM → 候选事件 → event-task/v1 核验 → 显式 fall 复核 → monitor/pickup/deliver → 原 MILP → Nav2/服务 ACK。这里同时有内容1、2、3的证据。

但不能把它扩大成“全部三项研究已经完成”。内容1尚未完成随机人体的通用三维定位和独立泛化评估；内容2的误报、TTL、空间有效性消融仍需独立实验；内容3的动态分配和局部修复只有有限实例，Fast/Standard时间目标未达，局部方法也没有普遍性能优势证据。
