# 脚本事件仿真、实车功能验证与Gazebo医院场景选择

日期：2026-11-09。本轮只完成独立事件—任务回放和只读资料调研，未下载医院场景、安装依赖、运行ROS/Gazebo或连接实车。外部项目信息核查于本日；下述匹配度是工程判断，不是已完成构建/性能验收。

## 1. 用户提出的实验分工可行

建议采用：**算法比较主要在独立仿真/Gazebo，实车主要验证真实感知、异构能力与任务执行；统一使用同一事件/任务协议。**

仿真可脚本注入“t=某时刻，B区域发生事件E1”，用地图区域/Marker表达位置，不需要跌倒动画。要检验第三项时固定事件、任务及扰动轨迹，可排除第一项识别误差对规划比较的干扰；第二项仍可回放有遮挡/位置失效的语义证据做独立比较。实车则由真实相机输出形成相同协议，检查全链是否适用。

这与[学长论文阅读评审](station_master_thesis_reading_and_project_positioning_2026-11-09.md)中的分层思路一致：论文第三/四章先MATLAB验证规划，第五章再Gazebo与小车执行；第19/63页明确省略具体搬运动作。因此可以对非研究对象合理抽象。**不能把脚本事件下的规划成功称为跌倒识别成功，也不能把模拟服务成功称为实际取放成功。**

用户提到规划、控制、避障：仿真可以测试这些层的综合执行，但若本项目复用Nav2局部控制/避障，应写作支撑技术及系统有效性，不能把它们的既有效果改称新控制/避障算法。声称改进某层时，才需要该层匹配的对照。

## 2. 无跌倒动画仍可体现动态场景

动态性由任务、空间和执行条件随时间变化体现，不由动画精细程度决定。建议把“动态任务变化”与“动态通行/执行变化”分开报告：

| 场景 | 时间变化 | 支撑结论 |
|---|---|---|
| S0无事件 | 多机完成常态任务 | 基础可行性、无误触发 |
| S1突发事件 | 已执行常态任务后注入E1，生成监护/取送并改派 | 在线事件驱动的任务重分配 |
| S2通道/空间变化 | 执行中关闭一条边、放置带碰撞/激光响应的移动障碍或更新服务点 | 可达性/资源变化后的修复；用于动态空间主张 |
| S3执行变化 | 行驶延误、到达后启动条件未满足、任务/取消ACK延迟 | 实际执行反馈驱动的计划更新 |

初期主场景用S1，再增加S2/S3中的有代表性扰动即可，无需一开始实现完整人群行为。只在静态图上离线算一次任务或播放预先生成轨迹，不能充分支撑执行期动态适应性。

避障实验中的移动障碍必须在传感器/代价地图或显式空间状态中生效；纯人物渲染动画不自动等于可检测/可碰撞障碍。各方法使用相同事件时刻、目标、障碍轨迹/关闭区间、初始状态和成本；仅算法不同。记录任务完成、响应、资源违规、计划变化、求解时间及真实运动反馈。

## 3. 实车不必重跑全部算法对照，但仍需测量

可以把实车设计成若干功能场景，不要求把所有MILP基线、全部随机种子和规划对照在实车重跑。它应证明：真实人体证据可以形成有效事件/目标，机器人能按分配到达、启动、完成/失败反馈；不同能力会影响分工。

不过，“不重跑全套算法比较”不等于“只留成功视频、完全不报告数据”。建议每场景重复若干次，记录次数/成功率、识别到任务启动的延迟、目标误差/到达、超时和失败原因。第一项若主张识别效果改善，仍需在独立数据或受控回放中保留定量比较，不能由几个实车成功案例替代。

可选实车场景：A正常/坐下等日常活动无处置误触发；B真实人体异常证据→核验/监护；C能力不同的机器人完成监护与模拟取送；D短遮挡或目标无效时保持事件但不派发假目标；E一次启动失败/取消确认。场景按硬件能力收敛，不强求全部实现。

异构性应有具体依据：传感器、携物装置、载荷、速度或明确可验证的能力限制。相同机器人只改R1/R2名字不是异构证据；只有单台实车时，论文应称单机子链验证，多机/异构主要由仿真或其他实际设备支撑。没有机械臂/装卸装置时明确取送为带反馈的服务模拟。

## 4. 医院场景候选与当前建议

已核对仓库现有world采用Ignition系统插件，已有TurtleBot4 Ignition入口；版本迁移成本必须考虑，不能仅看到仓库名有ros2就视为兼容。

| 项目 | 已核实内容 | 本项目使用建议 |
|---|---|---|
| [Open-RMF Clinic / humble](https://github.com/open-rmf/rmf_demos/blob/humble/README.md#clinic-world) | Humble分支注明Ubuntu22.04、Humble、Fortress；Clinic含双层、升降机和不同角色车队 | 优先做场景资源可提取性小审计；先取单层，不把门、电梯和全套RMF都引入主实验 |
| [AWS Hospital World / ros2](https://github.com/aws-robotics/aws-robomaker-hospital-world/tree/ros2) | 有医院world/素材；[启动文件](https://raw.githubusercontent.com/aws-robotics/aws-robomaker-hospital-world/ros2/launch/hospital.launch.py)依赖gazebo_ros的gzserver/gzclient，即Classic链 | 可借医院几何与素材，但须改配Ignition插件/资源URI等并核验碰撞；不是现有栈的即插即用包 |
| [hospital-agv-sim](https://github.com/Narcis-Abella/hospital-agv-sim) | 作者README注明Humble/Fortress、Tracer2和医院环境，侧重传感器噪声 | 可作同版本医院world候选；需检查资源齐全/许可及替换机器人代价，不整体接入无关噪声研究 |

AWS原库[已归档](https://github.com/aws-robotics/aws-robomaker-hospital-world)，旧代码需从历史分支取，不能按默认archive分支期待完整world。Open-RMF当前main的软件组合也不同于humble分支，应固定分支/commit。上述均未在本机运行，维护状态和兼容性不能仅靠README保证。

**推荐顺序是工程判断**：先保持已有house环境做协议/执行回归，同时小规模比较Clinic单层资源与hospital-agv-sim的world完整性；选择移植成本最低的一个作为医院主实验。AWS素材可作备选，不先花大量时间追求视觉逼真。场景只是实验载体，不能代替自己的事件与规划方法。

Open-RMF本身含任务分配与交通协调。若为了使用场景直接运行整套RMF调度/协调，必须标明其职责；评估本项目规划器时应隔离原调度器，或把RMF单列为对照，不能把它的避冲突与分配表现计为本项目收益。同样应核对demo机器人是否使用真实Nav2/传感器闭环，而非理想轨迹驱动。

## 5. 选定前应检查的最小清单

只读/离线小审计后再迁移：固定commit与许可证；检查SDF版本、Classic/Ignition插件、模型/mesh/纹理/Fuel可用性、碰撞体、坐标尺度/楼层、静态地图对齐、走廊净宽与机器人footprint、传感器/TF和多机命名空间。先验证单机导航/到达反馈，再放2–3台、加脚本事件和瓶颈通道；暂不做电梯/多楼层调度。

不因换医院world而覆盖已有地图/launch/规划配置。应该新建独立场景入口并保留旧回归，先跑相同任务与事件协议。当前回放数据可作为脚本事件来源；后续仍须规划视图适配、求解与执行反馈，不是直接把JSON发给现有Nav2即可。

最终实验分工：E1感知数据比较；E2同证据事件/任务回放比较；E3独立/Gazebo规划比较；E4实车有限功能与执行验证。这样既允许简化非研究对象，又保留题目动态性的实际证据。
