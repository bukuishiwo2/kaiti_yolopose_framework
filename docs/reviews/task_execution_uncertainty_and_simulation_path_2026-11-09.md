# 从任务级计划到实际执行：启动条件、不确定时长与Gazebo验证边界

日期：2026-11-09。本文是设计分析，**没有接入ROS/Gazebo，也没有实现下列执行扰动或改动原规划执行主链**。本轮实际代码工作是独立任务级仿真的完整流程计时消融，结果另见`reports/benchmarks/task_repair_ablation_2026-11-09.md`。

## 判断

接机器人或导航仿真时，必须考虑规划耗时、通信/调度延迟、实际行驶、末端对准、任务启动确认、服务耗时、失败与恢复。任务不能因为“计划时间到了”就启动，也不能以浮点坐标完全相等为到达条件。

Gazebo适合验证底盘运动、传感器/定位、Nav2局部控制和任务启动门限是否匹配；它不能替代MILP同范围正确性验证、收益归因或大量可控扰动实验。建议本轮完成归因，再补独立执行扰动与反馈契约，随后复用仓库已有Gazebo/Nav2环境做少量闭环验证。无需从零另搭仿真世界，也不应直接把所有算法对照搬到Gazebo。

这不是抽象担忧。[七月S1审计](public_space_v3_s1_closure_2026-07-29.md)记录：地图与world对齐后A/B/C/D/S路径检查通过，但D→S连续导航仍在120.016仿真秒超时，发生11次恢复，墙钟耗时471.064秒；日志含`Failed to make progress`。这是历史执行记录，不能当作本轮重跑或当前机器人状态。说明“存在全局路径”不能推出“按预计时刻实际到达”。

读取当前[`milp_plan_executor_node.py`](../../ros2_ws/src/yolopose_ros/yolopose_ros/milp_plan_executor_node.py)可见：队列分发检查waypoint/map、TF、Nav2 action server；导航结果非成功时按上限重试/报告失败，成功后推进step并可能将task记完成。这条通用导航队列逻辑不能直接作为“监护已建立/物品已取到/交付已确认”的任务动作证据。需要显式的任务服务反馈契约，而不是把导航成功等同于服务完成。

## 应明确的执行状态与启动条件

建议任务执行状态至少区分：

`QUEUED → NAVIGATING → ARRIVAL_CHECK → WAITING_PRECONDITIONS → STARTING → EXECUTING → SUCCEEDED`。

导航、到达/对准、前置条件等待、动作启动确认和动作执行均有各自超时与失败原因；失败不是无限等待。取消请求后先等确认释放，再将机器人或资源重新分配。状态方案属于待实现接口设计，不表示现有系统已具有这些状态。

设计划开始为s̄_j、任务释放为r_j、前驱实际完成为f_k，启动应由当前真实反馈决定：

`t_start(j) = 首个 t ≥ max(s̄_j, r_j, 所有前驱实际完成时刻) 且 G_j(t)=true 的时刻`。

G包含：

| 条件 | 应验证的真实反馈 | 失败后对规划的影响 |
|---|---|---|
| 到达且稳定 | 位于任务允许服务区域，位置/必要朝向误差和速度达标，持续一个稳定时间窗 | 延迟、换服务点或导航失败；不能仅因预计行驶时间耗尽便算到达 |
| 定位与信息有效 | map坐标/TF一致、位姿与目标新鲜、误差/协方差在允许范围 | 暂停启动，刷新位置或触发重新定位/任务目标更新 |
| 任务自身就绪 | 监护需人体进入有效视野；取物需物资/执行装置确认；交付需交付确认 | 更新任务状态与时长，必要时重新选择执行者 |
| 依赖满足 | 前驱实际完成；取送同机；需要时监护当前仍有效 | 前驱延迟应向后传播，不能使用原计划完成时刻替代 |
| 资源与安全条件满足 | 实际取得资源使用权、共享区域未冲突、服务点满足人体安全约束 | 更新实际占用/预约并传播影响，不得仅依赖过期时间表 |
| 时间、电量可行 | 仍在任务启动/完成期限内，有执行及返回余量 | 迟到或低电量需显式重规划/报告不可行，不能静默放宽期限 |

到达门限应针对任务定义。例如某巡检允许一个区域内稳定观测，取放可能要求更精确位姿；不统一要求机器人中心到达同一个数学点。需要朝向的任务可使用位置误差≤εp、角度误差≤εθ、速度≤εv，并保持δ秒。各阈值应由任务需要、机器人实际精度和试验测量确定，本文不预设通用数值。

Nav2 Humble的[SimpleGoalChecker源码](https://api.nav2.org/nav2-humble/html/simple__goal__checker_8cpp_source.html)已经区分位置与朝向容差；[SimpleProgressChecker源码](https://api.nav2.org/nav2-humble/html/simple__progress__checker_8cpp_source.html)根据移动半径和允许时间检查进展。它们是导航层机制，仍需与任务服务门限协调。不要在Nav2允许0.25m误差、任务却要求0.02m时无限等待，也不能为“让实验通过”任意放宽实际安全/操作要求。应选择匹配的导航目标和服务区域，必要时增加有上限的精对准步骤；超时后返回明确原因。

可按原因区分`NAV_TIMEOUT`、`ARRIVAL_NOT_STABLE`、`LOCALIZATION_STALE`、`PRECONDITION_TIMEOUT`、`ACTION_START_TIMEOUT`、`ACTION_FAILED`。同一事件/任务/计划版本/执行尝试的请求需幂等，避免超时重试导致重复取物、重复交付或资源重复释放。

## 时间和计划更新

需要分别记录：检测/确认、事件进入规划、求解开始/结束、计划发布/接收、导航分发/到达、对准完成、启动请求/确认、服务开始/完成、取消请求/确认、资源取得/释放。

- **求解时间**：使用monotonic墙钟，报告整个修复流程，包括不可行范围、扩展、回退和验证。
- **任务响应时间**：使用真实机器人时间或ROS仿真时间，贯穿感知到实际服务启动/完成，不能只报MILP给出的s_j。
- **仿真时钟/墙钟**：Gazebo运行慢于实时或暂停时不能混用；仿真目标超时与进程墙钟看门狗分别设置、分别记录。
- **执行中求解**：现实里机器人通常继续执行有效旧承诺。新计划计算完须按最新世界状态/计划版本复核，必要时重定基准或拒绝过期计划，不能直接发布基于数秒前状态的计划。

本轮独立DES的求解期间虚拟时间暂停，因此其虚拟响应仅验证计划逻辑，不证明上述在线效果。下一轮扰动DES应让计算延迟作为可控事件，机器人执行不暂停；用相同外部扰动/工作负载比较策略，并另外记录本机实测求解时间。若把实测求解耗时映射到仿真时间，应显式定义映射，并在Gazebo里通过实际ROS clock区间复核；不默认“1墙钟秒=1仿真秒”。

实际服务时长可拆为行驶、排队、对准、启动确认、服务。首先从Gazebo或实车日志估计各段分布/区间，再决定采用时间余量、区间鲁棒或机会约束；不在无数据时任意宣布一种建模就是创新。事件或执行延迟导致预约失效时，应更新占用并影响相关机器人；正在监护时若人体失去可见性，不能沿用旧布尔标记声称覆盖持续成立。

这仍属于原第三项“变化后维持可行性并减少不必要计划调整”：执行偏差提供扰动输入，分配与排程算法处理受影响的任务/承诺。到点门限、重试和接口本身通常是工程基础，学术贡献要看不确定时长或执行承诺如何建模、算法如何处理，以及相对公平基线的证据。

## 建议的验证顺序与进入Gazebo的门槛

1. **本轮完成流程消融**：同保留/扩展策略下单体与分解使用同范围、同预算、同目标，多轮交错计时。回答算法收益归因。
2. **下一轮独立DES执行扰动**：在相同种子与扰动轨迹下加入行驶超时、到达后对准延迟、定位抖动/过期、启动确认丢失、服务超时和资源占用延长，允许实际执行反馈触发重规划。先定义超时处理、活动任务保留/取消确认、实际资源释放和过期计划拒绝；检查不会无限等待或虚假成功。这是建议，尚未实现。
3. **Gazebo/Nav2最小闭环**：先一台机器人验证“导航→稳定到达→任务启动/完成或失败”；复用现有环境并先重验七月D→S未通过的基线。再加入第二/三台机器人、共享瓶颈和跌倒事件，使用相同事件、能力和任务契约。人体事件可以先脚本注入以固定第一、二项研究输出；随后再用相机感知端到端验证。
4. **实车**：用仿真已验证的契约重新标定位姿容差、时长分布和耗电，检查模型偏差；仿真成功不自动代表实际机器人通过。

进入Gazebo前的合理门槛是：共同规划模型与完整流程对照已通过；执行状态/反馈格式固定；到达/启动超时有明确处理；可以从日志还原“为何迟到、为何重分配”。不要求先解决所有执行不确定性才碰Gazebo；也可以用已有Gazebo做独立的行驶/对准数据采集，帮助校准DES，但不要让这些采集替代受控算法对照。

Gazebo阶段应报告导航/任务成功率、虚假到达或启动次数、到达至启动延迟及超时率、端到端响应/完成时间、实际资源冲突、电量/返回余量、计划变动、重规划次数和全过程求解时间，同时记录real-time factor、ROS版本、地图/world、导航参数和随机种子。参数与阈值不得逐算法单独调优。
