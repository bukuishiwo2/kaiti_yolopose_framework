## 1. 推荐路线与研究问题

保持第三项研究内容：**已有常态任务正在执行，新事件引入有依赖和角色约束的处置任务后，怎样更新多机器人分配与排程，在满足执行承诺和资源约束的同时，减少不必要的计划调整与在线求解开销？**

推荐最终实验链：Clinic的L1固定地图/几何 → 三台带传感器和Nav2的机器人 → 脚本事件 → event-task/v1 → 独立MILP策略适配 → 分机器人执行 → 实际状态反馈。首先完成一次事件的闭环，再研究执行偏差导致的重复修复。无需摔倒动画，地图事件标记与任务状态足以表达触发；动态性由事件、任务集合、实际执行状态与计划随时间变化提供。

算法先以**结构保留＋全局时间联动＋必要时逐步释放＋单体MILP**为重点候选策略；把同策略分解保留为消融。不能把“接上Gazebo”“成功到点”或“工程接口”本身称为规划创新。

能力示例沿用已有仿真的部分重叠：R0={move,camera,carry,patrol}，R1={move,camera,carry,patrol,inspect}，R2={move,carry,patrol,inspect}。若三台使用同一底盘，只能称**预设功能能力异构**，camera/carry等由模拟服务能力限制，不声称硬件异构或真实装卸。后续可替换为不同机器人模型，但不是第一轮必要条件。

## 4. 接入模块与数据边界

拟用独立命名空间`/clinic_experiment/*`，JSON沿用项目现有传输习惯；这些topic目前不存在。不要直接往生产`/planning/plan`发布另一套未兼容的任务结构。

| 拟议组件 | 输入 | 输出/职责 |
|---|---|---|
| 场景事件源 | 固定场景脚本、ROS仿真时钟 | event-task/v1 observation/resolution/tick；不访问算法分配结果来选择对其有利的事件 |
| 协议适配器 | observation、实际服务反馈 | planning_view；持久ID、revision/attempt、completed_facts和active_commitments |
| 快照构造/模型编译 | planning_view、机器人实际状态、物资owner、资源占用、参考计划、travel-time表 | 同一版本的MILP输入；完整依赖、覆盖、能力、电量与活动前缀 |
| 独立规划进程 | 固定输入、policy、统一目标/预算 | 候选计划、范围/回退轨迹、求解状态、独立约束检查 |
| 计划协调与执行器 | 经复核的plan、任务守卫、Nav2反馈 | 每机导航与服务状态；取消ACK、失败原因和实际开始/结束；失效旧计划队列 |
| 记录/独立评估 | 所有计划、反馈、Gazebo状态、时钟、资源记录 | 可重建时间线、约束审计、前后计划图、指标和失败明细 |

基本身份链：`run_id / event_id / task_id / world_revision / plan_revision / task_revision / attempt / robot_id / goal_id`。命令、反馈、取消确认按这一链匹配，旧尝试的迟到成功不能完成新尝试。

参考计划取最近一次实际提交并生效的计划，不取尚未提交的候选解；实际已完成事实优先于任何预测。第一次事件前各方法参考计划相同，后续闭环分叉后分别相对各自最近承诺计变化，再统一报告相对初始常态计划的累计变化。

状态至少区分QUEUED、NAVIGATING、ARRIVED、WAITING_GUARDS、SERVICE_RUNNING与完成/失败/取消过程；它们是执行器内部状态，协议对外仍按现有started/succeeded/cancelled表达。Nav2成功只表示导航结果，不自动代表核验、监护或交付完成。Humble的[NavigateToPose接口](https://api.nav2.org/actions/humble/navigatetopose.html)给出目标和反馈；最终成功/取消/失败还应读ROS action状态，不能因result载荷为空而推断成功。

## 5. 按门槛推进的具体步骤

### P0：固定场景输入与计量口径

先定义L1中的基地B0/B1/B2、巡视点P1/P2、检查点I、物资点S、事件区域E、核验点V、监护点M、交付点D和可等候点H。坐标需在实际地图上选择并验证，不能照搬DES的(2,1)、(6,4)。V/M/D位于给定人体安全区域之外；本阶段安全区域为配置输入，不把圆/矩形标记称为安全区生成算法。

冻结机器人能力、初始位姿、电量、常态任务清单及释放时间、事件脚本、期限、服务时长、目标权重、预算与超时策略。先测常用路径段的行驶/转向/到达时长，以路径长度、速度、转弯和公共余量建立机器人相关的有向travel-time表；无路为不可行，禁止用大但有限的数假装可达。现有tau需在**新独立模型适配版本**中统一替换，模型、目标、重建和独立检查器都使用同一张表；之后重新进行同范围单体/分解核对。不要只替换目标函数或只给Nav2换目标。

阶段产物：场景manifest、地图/参数/源码哈希、可达点与路线表。验收：每个服务点可达，至少两种任务分工可行，候选模型没有悄悄删约束。首次标定数据与正式测试运行分开；参数固定后再跑对照。

### P1：单机与三机常态执行

先单机验证“导航接受→稳定到达→前置条件满足→服务started→服务succeeded”。到达门限包含位置、朝向（任务需要时）、低速度保持时间和定位新鲜度；与Nav2 goal checker精度相容。门限和导航/对准/启动超时由服务需求与预试验标定，禁止算法各调一套。到点但不满足启动条件必须有超时结果，不能无限等待或按预计时刻写成功。

再部署三机，执行6项常态任务N0–N5，包含巡视、检查、物资站服务。实际前驱完成、服务区互斥、返回基地、电量阈值均从反馈检查。不要先加入跌倒来掩盖原本就未通过的导航问题。

阶段产物：单机/三机常态日志、规划与实际执行时间图。进入P2的门槛是预试验任务均完成且无假成功、重复服务、控制竞争；发现失败就归因并修复，不能只删除失败轨迹。

### P2：事件协议和MILP对接，先做一次事件闭环

用event-task/v1替代实验链中的旧TaskFactory，保留旧DES不动：

1. 在常态任务执行过程中按脚本注入E1 confirmed及有效空间，先只释放verify。
2. 调度verify并导航到V；服务模拟桩在到达/启动守卫满足后执行核验，返回显式fall/no_fall。脚本设定fall表示核验结果模拟，不是相机检测结果。
3. fall核验成功后，生成monitor/pickup/deliver完整未来任务图。此时可联合规划三者，但不能把PENDING当作可执行READY。
4. monitor到M并实际started后才允许pickup开始；pickup实际完成锁定物资owner；同一机器人去D交付，监护者与取送者不同。
5. deliver实际完成后，monitor才允许结束并反馈成功；正常任务按新计划继续，最终返回基地。

事件源需按同一逻辑脚本给出位置刷新与tick，避免不加说明地沿用10秒回放TTL造成任务在导航中全部过期。TTL、刷新频率是场景显式参数，所有方法一致；无效位置/遮挡另做独立测试，不暗中永久有效。

第一次把事件安排在三台机器人已开始常态定时服务的公共时间窗口，便于核对当前模型的不可抢占前缀；各方法共享同一初始计划和触发前状态。跌倒后的核验与响应可以造成两个规划回合；首轮只保证在监护/取物开始前求解响应图，执行中若出现超出容差的偏差，记录失败/安全保持，不声称现有模型已经支持中途再修复。

阶段产物：完整版本化计划与执行日志、改派/顺延前后图、10项任务的实际执行记录。注意原DES是6常态＋3响应=9项；采用本协议后增加verify，总数为**10项**，不能继续把9/9当完整协议闭环。

### P3：接入实际时间、失败与中途修复

这一阶段需要扩展独立模型和执行契约，属于后续实现，不能假定现有函数已能处理：

- 将已完成事实、正在导航/服务/监护、已取物待交付和取消待确认区分。已装货owner固定，监护覆盖既有实际区间与后续交付；正在占用的资源不因计划取消请求立即释放。
- 行驶前缀先采用到下一安全边界再改派的共同策略；若研究中允许中途取消，须先取得取消ACK及最新位置，再构造新起点。各算法使用相同抢占规则。
- 求解放独立进程，Gazebo和有效旧承诺继续运行。求解使用monotonic墙钟；事件响应和实际执行使用ROS仿真时钟。另记求解期间实际推进的仿真时长，不假定墙钟与仿真秒相等。
- 计划返回时核对最新事件/任务版本、已完成事实、活动承诺、当前位置、电量与期限。正常执行进展可重定时间基准后完整复核；目标/owner/已完成事实冲突则拒绝过期计划并重新构造快照。不能只检查revision而忽略机器人已移动。
- 实际开始晚于预计、定位过期、服务启动超时或监护失效触发明确反馈。当前协议没有失败/健康度消息，需在独立扩展契约中定义后才接入；不伪造succeeded/cancelled来表示失败。
- 所有方法使用相同总预算和终止策略。UNKNOWN不是不可行，不因此逐步释放；当前实现只接受OPTIMAL，不默认支持“限时可行解”。若新增限时可行解模式，需统一验证incumbent与界，再作为单独实验设置。

阶段产物：含执行中多次扰动的审计；无无限等待、无旧计划覆盖新事实、无虚假完成。无可行计划时维持已有效执行或安全等候并显式报告失败；不能放宽硬期限后仍算原问题成功。

### P4：共享通道和能量压力，按实际模型扩展

第一轮先验证已有物资站服务资源。共享通道若作为论文结论，必须进一步定义路线的入口/出口、占用区间、方向/容量、前后安全间隔、入口等待点和实际释放确认，把已在通道内的占用传入模型。给任务填同一个resource字符串不能代表行驶全过程互斥。

共享固定路由下的占用时序可以先实现；若再联合选择路线，就要同步增加路线选择与预约变量、相同范围MILP和独立检查，明确这是新增模型范围。所有方法共用路径/控制器和通道执行规则。Nav2局部避障不能替代通道预约或证明无死锁。

电量先使用共同、显式的仿真能量模型，按实际行驶/等待/服务积分、记录阈值与返回余量；原始60/5是归一化DES数值，不能写成Wh实测。若使用Gazebo电池插件，先校准单位与耗电规则，避免同时扣两份能量。无充电模型时只测试“电量与返航约束下的可行性”，不声称支持充电调度。

## 6. 展示重分配的具体场景

下表为拟议可视化脚本，不是实测最优计划。原始N3期限先按实测行驶时间设计，再离线用全量MILP核实各类场景可行；不把离线参考解传给在线候选算法。

| 时段/条件 | R0 | R1 | R2 | 要检查的行为 |
|---|---|---|---|---|
| 事件前 | 巡视N0，后续N3 | 检查N1，后续N4/N5 | 常态运输N2 | 三机都在执行正常工作 |
| E1确认后 | 核验或继续原承诺 | 按能力可参与核验 | 继续常态任务 | 由算法选核验者，不写死R0 |
| 核验fall后，宽期限 | 某具camera机器人监护 | 某具carry机器人取送 | 继续/顺延常态任务 | 只调时序也可成功，不强求改派 |
| 核验fall后，紧期限 | 例：R0转监护 | 例：R1取送 | 例：接管R0的N3 | 旧任务owner发生变化且所有硬约束满足 |

核验者、监护者和取送者由能力/位置/期限决定，上表角色只是展示意图。紧期限应构造为保留原owner无可行解、释放部分结构有可行解；宽期限则应允许不改owner。若预试验没有出现期望的结构，不事后删掉“不改派”的有效结果，而是检查场景假设。

引导/安全区域任务放到基本10任务闭环通过后：前者先模拟“到引导点开展服务”，没有人员模型时不称已验证人员疏散；后者区分“设置警戒点/发布区域约束”和真正几何安全区生成算法。不要为了动画扩展而削弱主实验。

## 7. 公平对照与实验分组

### 7.1 方法表

| 方法 | 范围策略 | 后端 | 用途 |
|---|---|---|---|
| F 全量重规划 | 剩余任务全自由，相同计划变化代价 | 单体MILP | 主要基线 |
| L 局部修复 | 独立适配的现有闭包/冻结时间策略，不可行后全量回退 | 单体MILP | 说明固定时间的局限，计入失败与回退成本 |
| R 结构保留策略 | 保留owner/相对顺序、全局时间自由；必要时逐项释放 | 单体MILP | 当前重点候选，避免把收益错归给分解 |
| D 同策略分解 | 与R完全相同的范围、扩展、停止规则 | MILP＋外部LP | 后端消融；不预设更快 |

L是共同模型上的独立适配，不是原生产函数耗时。原RMF调度器不直接作为主基线：若没有相同监护覆盖、同机取送、变化成本和电量/期限等语义，比较的不是同一问题。未来外部方法需在共同约束下适配；若无法适配，则单列任务覆盖范围，不给其性能排名作过度解释。

固定相同能力、初始计划、地图、导航/控制参数、路径时间估计、资源与取消规则、目标权重、预算和硬约束。所有计算包括建模、失败范围、扩展/回退、验证与提交，不能只报最终成功求解。目标值需与实际执行指标分别报告。

### 7.2 场景矩阵与建议样本数

| 场景 | 变化 | 核心问题 | 前置阶段 |
|---|---|---|---|
| S0 | 无跌倒，常态任务 | 环境/导航基础能力，非方法先进性比较 | P1 |
| S1 | 一次跌倒，常态任务宽期限 | 时间联动能否保留原分工 | P2 |
| S2 | 一次跌倒，常态任务紧期限 | 能否释放必要结构并改派 | P2 |
| S3 | 导航/到达或启动延迟 | 实际反馈能否更新计划，是否出现假成功 | P3 |
| S4 | 延长共享通道占用 | 预约变化能否传播，实际无冲突 | P4通道模型完成后 |
| S5 | 低电量但问题仍可行/另设确实不可行组 | 电量影响分工及明确失败行为 | P4能量模型完成后 |
| S6 | 重复观测、短遮挡、位置失效/恢复 | 是否重复任务、误取消或发往无效目标 | 协议/执行契约扩展后 |

先用种子7/19/43做P2小型预试验，不用于宣称统计优势。主实验建议S1/S2/S3各10个固定种子、F/L/R三方法，共90次；S3须等P3就绪再进入统计，不因排期强行冒充完成。种子应改变任务工作量、事件时刻/位置、服务延迟等真实输入，不只是改变几个任务的服务秒数。每组配置清单和设计规则在正式运行前冻结。

另取三类场景各5种子，对F/L/R/D做60次后端/流程对照；与主实验重复的轨迹可复用但不重复算独立样本。大量求解时间统计继续在固定快照回放中交错计时，Gazebo负责物理执行验证，不必用高成本画面重复全部计时。样本数是可执行起点，不是充分性定理；报告配对差值、离散程度和失败原因，不以少数成功视频支持优越性。

每个run重启独立实验进程并复位世界、任务/协议/电量状态；只移动模型回起点不保证控制器和协议复位。统一预热、就绪检查、超时和总时限。同机串行跑方法，打乱/平衡方法顺序，GUI录像单独取代表轨迹；headless和GUI结果不可不加说明混算耗时。

固定外部扰动由`(scenario, seed, task_id, attempt, disturbance_kind)`索引，避免不同算法调用随机数次数不同而得到不同难度。初始计划和事件前快照完全相同；事件后由于分配和执行不同，状态可以分叉，不能为了“同输入”把机器人强行改回相同状态。使用两个层次：固定快照回放隔离规划效率；配对闭环运行评价真实结果。主场景事件按统一仿真时钟触发；核验结束时刻是算法产生的结果，不强制相同。

## 8. 指标、审计与论文能说明什么

必须从实际反馈记录：

- 事件确认→核验开始/结束、确认→监护实际开始、确认→交付实际完成；另报核验成功→监护/交付，避免掩盖核验开销。
- 常态/响应任务完成比例、期限违约数与幅度；失败/不可行/UNKNOWN/无效计划分别统计，不只对成功轨迹计算响应时间。
- 旧任务改派数、已承诺相对顺序变化、未开始旧任务的开始总时移、导航取消/重新派发数；已完成/正在执行前缀单独核对。
- 完整修复墙钟时间、求解期间仿真推进、计划提交延迟、扩展/回退/拒绝旧计划次数、外部LP次数和预算超时。
- 导航成功率、到达→服务启动延迟/超时、监护覆盖缺口、同机取送与物资owner一致性、重复服务、实际资源重叠、碰撞/最小间距（按明确检测口径）、最低能量和返航余量。
- world/map/模型/算法参数哈希、ROS/Gazebo/Nav2版本、运行负载、仿真real-time factor和异常日志。

持续监护第一版为服务模拟：机器人在M持续占用，直到实际交付完成。即使做到这一点，也不是验证真实相机中人体持续可见。可后续加传感器视野/遮挡健康度，但健康度失效时要反馈，而不是沿用旧RUNNING标记。

独立评估器重建实际服务区间/路线/占用，不只复用规划器“合法”标记。预期时刻的MILP约束通过与实际执行约束通过分开报告。输出至少包括：事件前计划、事件后提交计划、实际执行三行甘特图；地图上的路线/角色变化；任务ID对应的before_after.csv；完整反馈和求解日志。示意图/一次成功演示与正式定量结果分开标注。

若R与F执行结果基本相同但完整求解更快、变化更少，只能据此提出对应的效率/稳定性价值；若所有策略结果相同，只说明它们在这些输入上都能工作。若D仍更慢，就保留负结果并不把它写成贡献。若导航误差主导，应查共同执行模型，而不是通过逐方法调Nav2参数制造算法差别。与最接近文献的模型/算法区别仍需独立论证，Gazebo成功不能代替新颖性证明。
