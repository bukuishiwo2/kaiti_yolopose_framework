# 公共空间新研究场景重构建议（2026-07-23）

## 1. 任务目标

根据 2026-07-21 组会后的建议，结合当前仓库中的研究方案、阶段审计、实验报告、系统工作记录和组会材料，回答以下问题：

1. 如何把“动态家居”替换为更容易展示动态性和任务规划价值的公共场景；
2. 新系统与普通扫地/清洁机器人相比，研究问题有什么本质区别；
3. 是否需要路径规划和三维场景建模；
4. 为什么当前选择 LSTM，而不是直接使用 Transformer；
5. 规划算法本身并非全新时，论文究竟增加了什么研究内容；
6. 如何最大限度复用当前已经完成的感知、MILP、LocalRepair 和 ROS2/Nav2 工作。

本文是阶段性场景评审，不直接覆盖当前冻结的
`docs/graduation_research_plan_v2.md`。只有在导师确认新场景后，才应按仓库变更控制规则形成 v3 研究方案、配置和演示世界。

## 2. 当前项目事实基线

### 2.1 已经形成的可迁移能力

当前项目真正可迁移的核心不是“家居布局”，而是以下跨层闭环：

```text
视觉人体姿态
  -> 关键点短时序分类
  -> 质量门控语义状态
  -> 稳定事件 episode
  -> 动态任务与空间资源状态
  -> 多机器人序列 MILP
  -> Nav2 执行与反馈
  -> Full-Replan / LocalRepair
```

截至 2026-07-17，仓库已经具备：

- `YOLO Pose + LSTM / TCN / 规则法` 的训练、推理和评估链；
- 四状态语义状态机、事件 episode、动态任务工厂和 revision 机制；
- 直接后继 arc 的序列 MILP、资源预约、电量约束和 validator；
- 五类扰动触发、影响传播、冻结前缀、LocalRepair 与 Full-Replan 回退；
- ROS2 world revision 驱动的 planner、单车 Nav2 执行器和地图/path audit；
- house 候选图上 `A -> B/C/D/S` 的 Nav2 `getPath()` 可规划性证据。

### 2.2 当前可以引用但必须说明口径的指标

现有开发集结果为：

| 方法 | Precision | Recall | F1 | 当前定位 |
|---|---:|---:|---:|---|
| 规则法 | 0.7558 | 0.4196 | 0.5396 | baseline / debug |
| LSTM 最佳开发配置 | 0.8657 | 0.7401 | 0.7979 | 默认主模型 |
| TCN | 0.8990 | 0.5882 | 0.7111 | 低误报对照 |

5% hard-negative 两阶段训练把 ADL 误报帧从 `273` 降到 `162`，下降
`40.7%`。但这些结果尚未建立严格冻结的独立 test 口径，因此在答辩中应称为
“当前开发集结果”，不能表述为未知公共场景上的最终泛化性能。

### 2.3 当前进度不能过度表述的部分

- W1-W5 算法门禁已经形成，W7 仍未完成最终签字；
- 候选地图已通过 `getPath()`，但尚未完成
  `A -> B -> C -> D -> S` 实体连续 `NavigateToPose`；
- Nav2 path-cost adapter 和 `kaiti_interfaces` 仍未完成；
- PlanSys2、3 车 namespaced 仿真和 2 车实物实验尚未完成；
- 当前 house world 是系统联调资产，不应继续作为新论文场景的最终展示证据。

## 3. 场景候选比较

评分为 1–5，分数越高越适合作为当前课题的新主场景。

| 候选场景 | 感知复用 | 规划必要性 | 动态展示 | 实验可行性 | 系统改造成本 | 结论 |
|---|---:|---:|---:|---:|---:|---|
| 医院门诊大厅—候诊区—连廊 | 5 | 5 | 5 | 4 | 4 | **推荐主场景** |
| 校园教学楼大厅—走廊 | 4 | 4 | 4 | 5 | 5 | 推荐降级场景 |
| 地铁/高铁站大厅 | 4 | 5 | 5 | 2 | 2 | 人群、权限和仿真复杂度过高 |
| 商场公共区域 | 4 | 4 | 5 | 3 | 4 | 可行，但应急任务链不如医院自然 |

医院公共空间的优势在于：

- 跌倒检测可以直接复用，不必把感知主线扩成泛化“所有异常行为识别”；
- 候诊区坐下、弯腰、捡物、短时躺靠等动作正好构成 hard negative；
- 跌倒核验、急救物资配送、现场引导具有天然的任务先后和应急时限；
- 连廊拥堵、事件处置区占用、物资点和充电位都可建模为动态共享资源；
- 可以在仿真和普通室内走廊中做受控验证，不要求进入真实临床业务。

若医院素材或受控实验许可难以获得，可把地点降级为“校园教学楼公共大厅—走廊”，保持完全相同的算法问题，只把急救物资站改为校内应急物资点。

## 4. 推荐新场景

### 4.1 建议题目

正式论文题目建议：

> 面向医院公共空间异常人体事件的多机器人协同响应与最小扰动任务修复研究

更聚焦、风险更低的题目：

> 面向医院公共空间人员跌倒事件的多机器人任务规划与局部修复研究

组会展示标题：

> 从“检测到跌倒”到“完成协同处置”：公共空间事件驱动的多机器人任务系统

不建议在题目中直接写“通用异常行为检测”。当前数据和模型只足以支撑跌倒、
倒地滞留及其易混淆动作，扩展到打架、追逐、盗窃等行为会引入新的数据集、标签体系和模型主线。

### 4.2 场景布局

最小公共空间包含：

| 区域 | 语义 | 对应旧场景对象 |
|---|---|---|
| `A / dispatch_area` | 服务台与机器人待命区 | 客厅 A |
| `B / waiting_area` | 候诊区、事件发生区 | 卧室 B |
| `C / outpatient_hall` | 门诊大厅、常规巡检区 | 厨房 C |
| `D / charge_room` | 设备间与充电位 | 充电区 D |
| `S / aid_station` | 急救包/警示设备存放点 | 物资点 S |
| `corridor_H` | 候诊区与大厅之间的公共连廊 | 原窄通道 |
| `event_zone_B` | 跌倒人员周围的安全处置区 | 原事件服务区 |

这组映射意味着，WorldState、task factory、MILP 和 LocalRepair 不需要推倒重写；
主要变化集中在场景语义、机器人能力、公共场景数据和可视化世界。

### 4.3 机器人分工

| 机器人 | 主要能力 | 典型任务 |
|---|---|---|
| R1 巡检核验机器人 | camera、speaker、patrol | 巡检、近距离复核、语音询问 |
| R2 物资配送机器人 | carry、patrol | 前往物资点、取急救包、送至事件区 |
| R3 引导/保障机器人 | speaker/display、patrol、charge | 人流提示、事件区警戒、低电量时充电 |

最低可实现版本仍可只使用现有的 `verify -> pickup -> deliver` 任务链；
`guide_flow` 和 `guard_zone` 作为扩展任务，不应阻塞第一版闭环。

### 4.4 冻结动态脚本建议

```text
t=0s    三台机器人执行大厅/连廊巡检和必要充电
t=30s   waiting_area 固定视觉传感器产生 fall_candidate
t=36s   质量门控后形成 fall_confirmed，创建稳定事件 E1
t=38s   最近的 camera 机器人接受 verify:E1
t=45s   corridor_H 因人群围观变为 TEMPORARY_OCCUPIED
t=55s   verify_result=needs_assistance，释放 pickup:E1 和 deliver:E1
t=65s   corridor_H 恢复，或由规划器选择等待/绕行
t=80s   物资送达、事件关闭，未完成巡检恢复
```

扩展扰动再加入：

- 第二个事件插入；
- 导航失败；
- 配送机器人低电量；
- 事件区持续占用；
- 固定相机遮挡导致 `perception_degraded`。

## 5. 新场景中的核心研究问题与解决方案

| 研究问题 | 新场景中的具体矛盾 | 建议解决方案 | 主要验证指标 |
|---|---|---|---|
| RQ1：不稳定视觉如何成为任务事实 | 人群遮挡、坐下/弯腰误报、track 中断会反复建任务 | 32 帧骨架 LSTM + 质量门控四状态 + event episode；遮挡时保留 episode，并创建 re-observe/verify | event-F1、误触发数、重复事件数、翻转次数、触发延迟 |
| RQ2：公共空间动态如何进入规划器 | 围观人群、连廊占用、安全区占用不能只作为 costmap 像素 | 把动态 costmap 聚合为 `FREE/TEMPORARY/BLOCKED`、可用时间和绕行代价；固定相机事件绑定 `camera_id + zone_id` | 状态识别延迟、路径可行率、等待/绕行误差 |
| RQ3：如何完成协同应急任务 | 核验、取物、配送、引导有能力、先后、时限和共享资源约束 | 直接后继 arc 序列 MILP，联合任务分配、路径时间、资源预约、电量、deadline 和事件优先级 | 响应时间、完成率、延误、路程、资源冲突、求解时间 |
| RQ4：动态变化后如何避免全局震荡 | 走廊拥堵或新事件可能导致所有机器人频繁换任务 | 影响传播 + 已执行/执行中前缀冻结 + 未受影响未来任务冻结 + 变化惩罚；局部不可行回退 Full-Replan | 修改任务数、重分配数、时间偏移、回退率、可行率 |
| RQ5：感知误差如何影响系统 | 分类 F1 提升不一定等价于任务系统更稳定 | 增加跨层实验：相同视频分别经过单阈值、迟滞和四状态 episode，再统计计划 revision、空任务、响应延迟和无效导航 | false task、plan churn、无效行程、端到端成功率 |

## 6. 为什么使用 LSTM，而不是直接换 Transformer

### 6.1 当前选择不是因为 Transformer “不能用”

当前 LSTM 的具体输入是：

- 每帧 `17` 个关键点的 `x/y/confidence`；
- 包围框宽高比、面积和有效标记；
- 每帧共 `54` 维；
- 在线窗口长度 `32` 帧；
- 当前模型为 2 层、hidden size 128 的单向 LSTM。

这个任务需要识别的是一个短时动作过程：

```text
站立/行走
  -> 身体高度快速下降、姿态旋转或支撑丢失
  -> 接近地面并保持
```

LSTM 对这种固定长度、因果、短时序输入具有足够的时序记忆，同时参数量、训练数据需求和移动端在线推理成本都较可控。

### 6.2 当前不把 Transformer 作为主模型的四个证据

1. **序列较短**：当前只有 32 帧，Transformer 的长距离依赖优势尚未成为主要矛盾。
2. **严格数据量不足**：当前最需要补的是独立 test 和公共场景 hard negative，而不是先扩大模型容量。
3. **现有误差主要来自数据与观测质量**：坐下、弯腰、捡物、遮挡和 track fragmentation 不会仅靠注意力结构自动消失。
4. **已有同口径结果支持 LSTM 主线**：当前开发集上 LSTM 的 F1 和 recall 均高于 TCN；系统首先需要可靠召回跌倒事件，再由四状态和 episode 控制误触发。

因此，答辩时应使用如下表述：

> 本研究不是预先认定 LSTM 永远优于 Transformer，而是在 32 帧短骨架序列、小样本和在线推理约束下，选择已有实验证据最充分的 LSTM 作为主模型。Transformer 保留为同特征、同 split 的扩展对照；只有当公共场景数据规模扩大且需要更长时间依赖时，才升级为主候选。

### 6.3 必须补做的公平验证

为了避免“凭经验选 LSTM”的质疑，应在冻结独立 split 后比较：

- Rule；
- LSTM；
- TCN；
- 一个轻量 Transformer encoder。

四类方法使用相同的 54 维输入、相同 32 帧窗口和相同 train/val/test manifest，统一报告：

- frame/window/event-level Precision、Recall、F1；
- ECE、Brier score；
- 参数量、单窗口延迟、端到端 FPS；
- 遮挡、坐下、弯腰、捡物等子集结果；
- 最终触发的 false task 和 plan revision 数。

如果轻量 Transformer 明显优于 LSTM，可以更新主模型；如果收益不足，则当前选择得到实验支撑，而不是依赖模型名称的新旧。

## 7. 规划算法“旧”在哪里，新内容又在哪里

### 7.1 明确复用，不包装为创新

以下内容应明确写成成熟技术复用：

- MILP 求解器使用 PuLP/CBC；
- Nav2 负责路径规划和局部避障；
- RTAB-Map/AMCL 负责建图或定位；
- PlanSys2 负责动作生命周期；
- LTLf 工具只负责规格转换和轨迹验收。

论文不应声称发明了 MILP、Nav2、LSTM 或任务规划本身。

### 7.2 本研究真正增加的内容

1. **面向规划触发的事件抽象**
   把逐帧跌倒概率、关键点质量和跟踪连续性变成稳定事件 episode，解决重复建任务和遮挡时事件丢失。

2. **面向公共空间的动态资源抽象**
   把连廊拥堵、事件安全区和物资点占用从像素级 costmap 转成规划器可消费的状态、时间窗、等待和绕行代价。

3. **应急任务链与多机器人序列联合建模**
   在同一模型中表达 `verify -> pickup -> deliver`、能力约束、同机配送、直接后继路径、资源预约、电量、deadline 和事件优先级。

4. **最小扰动局部修复**
   状态变化时通过前驱、机器人执行链和共享资源预约传播影响，只重算受影响子计划，并以重分配、时间偏移和顺序变化作为计划扰动代价。

5. **感知—规划跨层评价**
   不只报告分类 F1，还验证不同语义稳定化方法最终造成多少错误任务、无效导航和计划震荡。

这里最值得强调的不是“用了一个旧算法处理新场景”，而是：

> 建立了面向异常人体事件的跨层状态表示、受约束协同任务模型和可执行的局部修复机制，并用端到端指标证明感知稳定性会真实影响任务计划。

### 7.3 与扫地机器人的本质区别

| 维度 | 普通扫地/清洁机器人 | 本研究系统 |
|---|---|---|
| 触发方式 | 预设时间或覆盖区域 | 非预期视觉语义事件 |
| 任务结构 | 单一覆盖/回充 | 核验、取物、配送、引导、恢复巡检 |
| 机器人关系 | 单机为主，或简单区域分工 | 异构能力、任务先后和共享资源协同 |
| 动态变化 | 主要由局部避障处理 | 会改变任务集合、优先级、deadline 和机器人分配 |
| 规划目标 | 覆盖率、路程、电量 | 应急响应、可行性、安全资源预约和计划稳定性 |
| 扰动处理 | 重走局部路径 | 重构受影响任务子计划并保持未受影响计划 |
| 输出评价 | 清扫完成率 | 事件响应成功率、误触发、plan churn、资源冲突、响应时间 |

## 8. 是否需要路径规划和三维建模

### 8.1 路径规划：需要，但不是论文主创新

需要路径规划的原因：

- MILP 需要真实的任务间旅行时间和绕行代价；
- 机器人需要把任务分配结果转成可执行导航目标；
- 连廊拥堵时需要判断等待、绕行还是不可达；
- LocalRepair 需要消费导航失败和路径代价变化。

建议继续复用 Nav2：

```text
ComputePathToPose / getPath()
  -> path_exists、path_length、estimated_travel_time、route_resources
  -> MILP arc cost

NavigateToPose
  -> success / canceled / failed feedback
  -> WorldState revision
  -> LocalRepair / Full-Replan
```

研究贡献是“如何把路径结果变成任务规划约束并驱动修复”，不是重新写 A*、DWB 或 MPPI。

### 8.2 三维场景建模：当前不需要作为研究硬门槛

本研究使用地面移动机器人，最小场景为单层室内公共空间。正式实验只需要：

- Gazebo/SDF 中有可辨识的候诊椅、墙体、物资点、充电位和连廊；
- Nav2 使用二维 known map / AMCL；
- global/local costmap 表达动态占用；
- camera/zone 配置把视觉事件映射到地图语义区域。

不需要做高精度三维重建、点云语义建图或连续动态人体三维场景恢复。

只有在研究范围扩展到楼梯、电梯、多楼层、可通行高度或机械臂取物时，三维信息才成为必要条件。当前加入这些内容会明显稀释任务规划主线。

## 9. 新场景对现有工程的迁移方案

| 现有模块/资产 | 迁移方式 | 是否重做 |
|---|---|---|
| YOLO Pose、54 维特征、LSTM/TCN | 增加公共视角数据与 hard negative；模型接口不变 | 否 |
| 四状态与 EventEpisode | 增加 `camera_id/zone_id`、遮挡 degraded 和 re-observe 规则 | 小改 |
| WorldState/task factory | 把 house zone 名称换成医院语义；保留幂等任务 ID | 配置为主 |
| sequence-arc MILP | 新增可选 `guide_flow/guard_zone` 能力和任务；核心约束不变 | 小改 |
| LocalRepair | 增加 crowd occupancy 和固定相机 degraded 触发 | 小改 |
| house world/map | 保留为 W7 系统回归资产；另建简化 hospital public-space world | 新增，不覆盖 |
| Nav2 adapter | 继续完成当前 W7 path-cost adapter | 复用 |
| `kaiti_interfaces` | 先按领域无关字段完成，再增加公共场景枚举 | 复用 |
| PlanSys2 performers | `observe/verify/pickup/deliver/charge` 直接复用 | 复用 |

固定相机与移动机器人之间不需要做跨摄像头 ReID。最低方案采用：

```text
fixed_camera_01 + waiting_area
  -> event_id + zone_id
  -> 移动机器人到 zone 近距离 verify
```

这样既适合公共空间，也不会把课题扩展成多摄像头身份跟踪研究。

## 10. 实验设计建议

### 10.1 感知与事件实验

数据必须按“事件/视频”划分 train、val、test，同一事件和多视角不得跨 split。

重点 hard negative：

- 坐下与起身；
- 弯腰、捡物；
- 蹲下系鞋带；
- 候诊椅上躺靠；
- 地面清洁/检修动作；
- 遮挡后重新出现；
- 多人交错造成的 track fragmentation。

消融：

```text
单阈值
vs 普通迟滞
vs 四状态质量门控
vs 四状态 + EventEpisode
```

除分类指标外，必须报告：

- 每小时误触发任务数；
- 单事件重复 episode 数；
- confirmed/degraded 翻转次数；
- 从真实跌倒开始到任务释放的延迟；
- false navigation 和无效任务里程。

### 10.2 规划与修复实验

主场景采用 3 台机器人和 1 个事件，扩展到 2 个并发事件。

基线：

- Nearest Robot；
- Priority Greedy；
- Request-Response；
- Full-Replan；
- LocalRepair；
- Proposed Full（事件 episode + 动态资源 + sequence MILP + LocalRepair）。

扰动：

- 连廊短时占用；
- 连廊持续阻塞；
- 新事件插入；
- 机器人低电量；
- 导航失败；
- 视觉退化后重新观察。

指标：

- 首次核验响应时间；
- 物资送达时间；
- 任务完成率；
- deadline violation；
- 总路程、等待和绕行；
- 资源冲突；
- 修改、重分配、偏移和顺序变化任务数；
- 求解时间、gap 和 fallback 率；
- LTLf 三值结果。

### 10.3 系统实验

按风险从低到高推进：

1. 单车人工事件：验证 `event -> plan -> Nav2 -> feedback`；
2. 单车真实/回放感知：验证事件稳定化；
3. 3 车仿真：验证异构任务和共享连廊；
4. 2 车受控室内实验：模拟公共大厅，不要求真实医院部署；
5. 固定相机 + 移动机器人联动作为增强项。

正式演示应至少同时展示：

- 视觉事件从 candidate 到 confirmed；
- 事件任务动态生成，而不是预先写入计划；
- 连廊拥堵改变路径时间或任务开始时间；
- LocalRepair 保留未受影响巡检任务；
- Nav2 执行和反馈闭环。

## 11. 研究计划调整建议

### 11.1 不丢弃当前进度

当前 W7 未完成项应先收口：

1. 候选图的实体连续 waypoint runner；
2. Nav2 path-cost adapter；
3. `kaiti_interfaces` 替换 `String + JSON`。

这些工作与家居/医院无关，是新场景仍然必需的系统基础。

### 11.2 导师确认后的 v3 迁移顺序

| 阶段 | 工作 | 验收 |
|---|---|---|
| S0 场景冻结 | 确认题目、研究问题、最低任务链和不做内容 | 导师确认一页场景定义 |
| S1 配置迁移 | 新增 hospital scenario/regions/waypoints 配置，保持旧配置回归 | planning smoke 与 validator 通过 |
| S2 简化世界 | 建立单层大厅—候诊区—连廊 SDF 与 known map | A/B/C/D/S `getPath()` 和实体导航通过 |
| S3 公共场景感知 | 独立 split、hard negative、校准、轻量 Transformer 对照 | test 报告与 event-level 指标完成 |
| S4 动态闭环 | 固定事件脚本、crowd occupancy、LocalRepair | 3 车 20 次、零资源冲突 |
| S5 论文/演示 | 跨层消融、图表和录像 | 一键演示与章节结论一致 |

### 11.3 范围控制

第一版不要同时加入：

- 打架、追逐、盗窃等多类别异常行为；
- 多摄像头 ReID；
- 人群轨迹预测；
- 三维语义重建；
- 电梯和多楼层调度；
- 机械臂操作；
- 新 SLAM/导航/求解器。

这些内容都可以写入展望，但不应成为毕业设计主线依赖。

## 12. 建议的组会叙事

组会不要从“我把家居换成医院”开始，而应按以下逻辑讲：

1. **原问题**：家居空间小、动态性不易展示，多机器人规划容易被看成扫地机器人式调度；
2. **新场景**：医院门诊公共空间中的人员跌倒与倒地滞留；
3. **核心矛盾**：视觉不确定性、应急任务链、公共连廊动态占用和计划稳定性；
4. **方法保持**：LSTM/四状态 episode、动态资源、序列 MILP、LocalRepair；
5. **场景新增内容**：固定视觉传感器触发、异构核验/配送/引导任务、公共资源预约；
6. **当前证据**：感知开发结果、LocalRepair 对比、Nav2 path audit；
7. **下一步证据**：独立 test、公共世界、3 车动态实验和跨层指标。

一句话答辩口径：

> 本研究不是研究机器人如何覆盖一个房间，而是研究公共空间中不确定人体事件出现后，如何把视觉证据稳定地转成异构机器人任务，并在通道占用、导航失败和新事件插入时，以最小计划扰动完成协同处置。

## 13. 结构性结论

1. 推荐主场景为“医院门诊大厅—候诊区—连廊中的人员跌倒事件驱动的多机器人协同响应”；
2. 保持跌倒/倒地滞留为感知核心，不把课题扩成通用多类别异常行为识别；
3. LSTM 作为 32 帧短序列主模型有当前工程和开发实验依据，但应补轻量 Transformer 公平对照；
4. 路径规划必须保留并复用 Nav2，三维建模不是当前硬门槛；
5. 规划研究的新内容应落在跨层事件表示、动态公共资源建模、应急任务链、最小扰动修复和端到端评价，而不是宣称发明 MILP；
6. 当前 house 工作应保留为系统回归资产，先完成 W7 公共接口，再新增医院场景配置和世界；
7. 若医院数据/实验许可受限，校园公共大厅可作为不改变算法问题的降级场景。

## 14. 未解决风险

- 新场景的文献查新尚未完成，当前结论是工程与研究问题重构，不等同于已证明学术首创；
- 公共视角下的人群遮挡和目标尺度可能显著降低现有 pose/tracker 效果；
- 当前感知结果仍缺严格独立 test，不能直接迁移成公共场景性能承诺；
- 新 hospital world 会增加建模和地图验收成本，必须复用当前 W7 门禁流程；
- `guide_flow/guard_zone` 若同时进入第一版，会增加 task factory、performer 和能力配置工作量；
- 真实医院部署涉及隐私、伦理和安全审批，因此毕业实验应定位为仿真与受控公共走廊验证。
