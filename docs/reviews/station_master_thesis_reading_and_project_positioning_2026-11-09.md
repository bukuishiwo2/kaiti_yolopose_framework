## 核心判断

可以借鉴的主要是**研究问题—数学方法—算法实验—执行验证的分层**。论文没有为建图、定位、局部控制每个环节都发明新算法；它把研究集中在时序任务描述、系统建模和任务路径求解，再复用成熟导航工具落地。

不应把“硕士论文需要独立研究工作”理解为“每章必须发明一个普遍优于最新顶刊方法的算法”。但是也不能从这一篇论文反推“拼接现成模块、演示能跑就足够”。本项目仍需要明确问题、说明自己的方法差异、用合理对照支持对应结论，并承认简化边界。学位要求须以导师及所在培养单位要求为准，本文不作毕业保证，也不依据单篇论文判定学长工作的全面新颖性。

前面对本项目的评价偏重通用算法先进性，应把两个问题分开：

- 当前证据能否证明“分解比同策略单体MILP更快”？不能；新消融给出了反证。
- 当前研究是否因此没有硕士论文价值、必须换主线？不是。它已经形成耦合任务建模、计划修复方法及独立验证基础，后续可在明确场景下补足执行闭环与方法论证，而不强行保住分解效率主张。

## 学长的工作具体如何展开

### 第三章：时序任务到编队运动路径

第19页明确研究边界：考虑多个机器人协同搬运的路径，不实现具体搬运行为。机器人以虚拟刚体编队，任务是按顺序访问不同区域并长期重复，在电量限制下访问充电区。

方法链条是：障碍按编队尺寸膨胀 → Delaunay三角分割 → 区域与离散电量组成切换系统 → LTL转Büchi自动机 → 构造乘积自动机 → 搜索prefix/suffix任务路径 → 仿射向量场生成连续运动 → 编队机器人跟踪。

这部分确实研究了连续运动生成，不只是把几个导航目标点连线。仿射场处理三角形内的停留与经指定边界离开，区域路径由上层时序规划给出。第22页区分离线规划与利用实时位置/速度计算控制值的在线过程；这里的在线控制不等同于突发任务的在线重分配。

MATLAB实验（32–36页）主要展示重复搬运路线、去充电区后继续任务、连续轨迹，以及机器人相对距离保持。电量采用离散单位；第22页假设进入充电站即充满，不是实测充电过程。不能把这样的抽象实验解读为已经验证所有机器人电池和执行装置细节。

### 第四章：用Petri网处理多机器人状态组合

针对联合切换系统随机器人数量扩张的问题，将区域/电量状态表示为Petri网库所，机器人状态用标识体现；LTL转自动机后先选观测序列，再通过MILP求可以使能相应转换的变迁及机器人路径。实际求解器使用CPLEX（第52页）。

目标项包含减少变迁数量、减少需要移动的机器人数量，以及与多机占用相关的惩罚。文中从MILP(4-12)开始，检查路径是否可执行、观测是否偏移，再在必要时使用限制更强的(4-13)、(4-14)；增加中间状态能提高可执行性，但计算更重（40–49页）。

这提供的借鉴是：**先明确模型为何可实现任务，再说明更精细约束的计算代价**。不是只说“使用LTL＋MILP就是创新”。文中绪论已经介绍既有Petri网规划研究，因此不能仅凭第三/四章标题断言其全部机制从零原创。

MATLAB实验包括周期巡视、两个区域同步进入/持续占位、另一机器人巡视与充电。第54页说明通过不同移动速度协调同步到达，但在所读实验部分没有给出定位噪声、启动门限和同步容差的多轮统计。

第56页表格2报告：

| 机器人数量 | 切换系统模型状态/运算时间 | Petri模型状态/运算时间 |
|---|---|---|
| 2 | 228² / 124秒 | 228 / 15秒 |
| 3 | 228³ / 8小时 | 228 / 45秒 |
| 4 | 228⁴ / 超过10小时 | 228 / 82秒 |

这是论文作者报告的模型比较，本轮未复现。它针对“避免显式联合状态空间膨胀”这一论点选对照，**不是全面超过所有最新任务规划方法的比较**。

同时要准确理解：Petri网的结构/库所数量可不随同类机器人数量直接乘方增长，不等于MILP实际运行时间与机器人数量无关；论文表中时间也由15秒升到82秒。本项目应避免照搬“计算量完全不受机器人数量影响”的宽泛说法，异构身份、任务绑定与资源约束会带来不同的模型规模和求解难度。

### 第五章：用成熟导航工具执行上层规划

第58页说明前两章主要是MATLAB二维仿真，第五章再增加物理环境、传感器、ROS和执行终端验证。论文写明使用Ubuntu16.04、ROS Kinetic、Gazebo9.0。这是论文当时的软件记录，不是建议本项目迁移的版本。

第60–63页的实施链条：

`Cartographer建图 → AMCL定位/TF/里程计 → 全局与局部代价地图 → 第三/四章算法生成任务相关全局路径点 → 局部规划/控制 → 机器人运动`。

图5-5将上层给定任务、全局规划、局部规划、传感器地图和机器人控制分开。文中介绍DWA、TEB等局部方法；实物小车部分明确使用DWA跟踪全局路径点。没有把Cartographer、AMCL和DWA分别宣称为本论文新算法。

Gazebo实验以Astrobee编队按次序访问搬运区域、访问充电区为主要演示。**第63页再次明确省略具体搬运动作，只关注搬运路径。**因此可以验证任务路径执行与环境导航，不足以证明真实物体抓取、装卸、交付确认均已实现。

实物使用Nanocar小车，在室内建图后执行三个区域的长期顺序巡逻，展示RViz路径与真实小车画面（65–70页）。这是对整体部署框架的简化执行验证；不能把单小车巡逻证据扩张成异构多机器人全部协同机制的实车验证。

第五章所读结果主要为轨迹、截图与流程说明，没有形成与第56页表格同等的多轮执行统计。既不能因为有Gazebo截图就认为证明了算法先进性，也不能因此否定它在验证从抽象计划到运动执行方面的作用。

## 对本项目最重要的适用边界

1. **不能复制不同高度避碰。**第53页明确利用空间站失重环境预先指定机器人不同飞行平面，从而省去机器人间碰撞计算并删除相应目标项。本项目是同平面地面机器人，共享通道/狭窄区域必须通过预约、冲突约束及执行反馈处理。
2. **不能把静态任务展示当动态重规划。**第52页场景叙述提及异常后的支援，但第72页展望仍明确指出集中式事先规划面对突发情况应变较弱。不能从场景文字推断论文已经评估在线计划保持、部分结构释放或连续执行扰动。
3. **可以抽象任务动作，但必须如实命名。**若本项目不做机械臂取放，可把取物/交付建模为给定时长、带开始/完成反馈的任务动作；需说明是服务动作模拟，而不是完成了真实搬运。监护应至少验证可观测或用明确模拟信号表达，不能只靠机器人停在点上就默认有效。
4. **不必新增运动控制创新。**学长第三章把仿射场列入研究内容；本项目原三项内容并未要求提出新底盘控制器。可复用Nav2，把贡献集中在感知、语义事件/任务、协同分配规划。
5. **不能升级LTL实现声明。**学长真实使用LTL到自动机/路径的合成链；本项目当前LTLf主要用于规格与轨迹验收。可以如实采用任务图/约束到MILP、LTLf验收，不因参考这篇论文就宣称已有LTL自动任务合成器。

## 本项目建议如何收敛

三项研究内容保持不变：环境与人体行为感知；语义事件构建与任务生成；多智能体协同任务规划。**三项内容不自动等于三项各自全面领先的通用算法创新。**要由导师确认希望形成的独立贡献强度和论文结构，不倒过来为凑三个新名称改变主线。

第三项适合围绕以下研究问题继续做：

> 常态任务执行中出现人体异常事件时，如何表达持续监护、异地取送、能力、期限、资源和电量之间的耦合，依据真实执行反馈维持可行的联合分配与排程，并尽量保留仍有效的执行承诺？

可形成的独立工作包括明确的任务/承诺模型、时间与结构分别处理的修复方法、以及执行反馈下的验证。这些是**候选贡献方向**；新增约束的组合是否已被现有模型覆盖、保留/释放机制是否只是标准fix-and-optimize适配，仍应与最接近研究核对。不能只换场景或名称就断言新颖。

运动规划与执行建议分层：

| 层次 | 本项目负责输出/检查 | 可复用基础 |
|---|---|---|
| 语义事件与任务 | 人体/事件位置、安全区域、可达服务点、任务依赖与条件 | 第一项感知、地图/定位 |
| 联合分配排程 | 哪台机器人、先后/并发、监护结束、资源预约、必要重分配 | 当前独立MILP及共同验证器 |
| 几何路径与局部运动 | 机器人如何走到服务点、如何绕障、能否按要求停稳 | 现有Nav2与局部控制，不要求另提新算法 |
| 执行反馈 | 到达、就绪、启动、完成/失败、实际资源占用与电量 | 明确接口；延误/目标变化反馈给上层修复 |

任务层使用由地图路径估计的行驶时间/距离，不长期把Manhattan时间当真实运行时间；Nav2绕行或延误导致预约失效时，要反馈更新，不能声称两层各自可行就保证全系统安全。

已有[完整流程消融](../../reports/benchmarks/task_repair_ablation_2026-11-09.md)应作为算法实验基础：192次是重复计时、只有6个输入；同策略单体强于当前分解。保留`retained_milp`作为强基线和当前小规模研究实现，不再为证明分解更快而继续增加复杂机制。后续若发现分解在更大问题有优势，再另作规模对照，而不是把它设为毕业前提。

### 可控的下一阶段实验

| 实验层 | 需要回答的问题 | 建议最小内容 |
|---|---|---|
| 算法/任务级 | 联合分配和修复逻辑是否正确、为何有收益？ | 保留现有同模型对照；补少量不同能力/约束紧度与执行延迟，不无限堆重复计时 |
| Gazebo闭环 | 抽象服务点和计划能否转为实际运动/任务启动？ | 先单机验证导航到达、停稳、启动/失败；再2–3机常态任务中触发跌倒，展示监护、取送和必要改派 |
| 受控扰动 | 迟到或启动失败后是否反馈并重新安排？ | 至少覆盖行驶延误/通道占用，以及到达后不满足任务就绪条件；有超时、取消确认和失败记录 |
| 实物补充 | 实际感知与执行接口是否合理？ | 根据已有硬件做跌倒感知—事件—服务点—移动/反馈链；只有单台时明确仅验证该子链 |

可以开始复用已有Gazebo环境做这个最小闭环，不必先开发新SLAM、全新运动规划器或完整抓取系统。但应先固定最小启动/反馈/超时契约，以免只得到视频而无法解释是否真正完成任务。既有七月S1导航失败记录应先复验，避免把导航故障误当分配算法失效。执行设计细节见[已有评审](task_execution_uncertainty_and_simulation_path_2026-11-09.md)。

建议Gazebo保留一个主场景：多机常态巡检/搬运 → 固定时刻或脚本注入跌倒 → 生成监护/取送 → 记录改派与时移 → 导航并满足服务启动条件 → 完成或显式失败。随后增加一个延误场景和一个启动失败场景。先固定任务输入比较第三项，再接真实感知做整系统演示，避免把误检差异算作规划收益。

除了视频/轨迹，应输出：原/新任务甘特图、实际服务启动与完成时间、事件响应、任务成功/超时、真实资源冲突、计划改动、求解时间。规划模型限定什么，实验就验证什么；没有操作装置、人体真实引导或区域封控，就明确为对应服务动作/语义任务的模拟。

## 是否必须超过最新研究

**不需要在所有维度优于最新方法，但需要知道与最接近方法的关系，并使实验与贡献主张匹配。**

- 若主张更快，必须对同问题、同约束、同预算的强基线验证；不能回避已经更快的同策略单体MILP。
- 若主张新的耦合任务表达，应说明现有模型缺少什么、为何影响计划、自己的约束/状态如何解决，并检查是不是已有模型可直接等价表达。
- 若主张更好的执行承诺保持/在线修复，应比较可行恢复、任务质量、改动和计算预算的权衡，而不是要求每一个指标都最好。
- 若主要贡献是特定场景的系统化方法与执行闭环，需清楚区分复用、适配和原创部分，并用定量案例验证实际价值；“接通了ROS话题”“修复了配置错误”“视频看起来成功”本身不能替代研究贡献。
- 不必把每个最新论文都复现一遍；但对最接近且足以覆盖自己主张的方法，应做机制级比较，并在可比范围内选合理强基线/清楚标注适配。不能通过“不追求SOTA”回避查新和公平比较。

学长论文提供的积极参照是：使用成熟工具，围绕明确问题形成数学描述、求解过程、分层实验和可解释边界。它不提供“当前项目肯定够毕业”的证明，也不意味着可以照搬2024年的比较范围、文字概括和实验统计粒度。
