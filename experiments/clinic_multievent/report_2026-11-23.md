# Clinic多事件表达扩展、S4只读诊断与LTLf独立验收

## 1. 结论和实际范围

本轮完成独立多事件语义registry、活动监护剩余区间MILP、事件/任务索引化编译、完整独立验证及真实历史日志的LTLf接线。没有更换CBC、调目标权重、放宽导航或服务守卫，没有启动Gazebo或连接实车。

正式能力输入7项，结果为5 PASS、1 INFEASIBLE、1 BLOCKED；44项来源/状态检查和934项完整方案约束检查通过。相关回归70项通过。本轮不是B3算法排名，也不是新的真实多事件三机闭环。

正式Clinic执行主链仍是单事件入口。新的全局registry能够在独立入口导入真实E1活动状态并接收E2，不覆盖E1的历史、owner、目标或token；尚未把该入口接到正式视觉执行器。所有新优化输出均execution_authorized=false。

证据根：`/home/yhc/clinic_planning_ws/verification/multievent_2026-11-23_k1`。以下相对路径均以此为根。研究主线仍为语义事件驱动的动态协同分配，执行承诺和修复提供保障，不重写三个研究内容。

## 2. 原单事件限制的位置、触发条件和原因

| 层次 | 实际位置 | 限制及设计原因 |
|---|---|---|
| 原实验MILP | 实际工作区tools/clinic_milp_backend.py，Model._build的events循环 | 每个event的monitor/pickup/deliver必须都在tasks，否则抛出原异常。其时间变量、同车与异角色约束均直接索引完整未来三角色，不能解释被投影到前缀之外的活动monitor |
| 原模型资源 | 同文件共享resource循环 | variable-duration monitor共用资源会被拒绝；原实验假设监护点独立。不能只加第二个事件后忽略这种可变区间互斥 |
| 原问题编译 | 实际工作区tools/dense_tasks.py | 拒绝活动monitor及携货；旧问题只在取货前或事件结束后提交。活动修复通过bed_contract另作预测前缀，并非通用活动事件模型 |
| 独立分配入口 | src/kaiti_task_sim/clinic_assignment.py | response、greedy、handover和B2第三角色规则硬编码E1；单纯让native events容纳两个字典并不能使目标、greedy和业务约束事件化 |
| 事件协议 | src/kaiti_task_sim/event_protocol.py | 类明确one episode per replay，只有self.event；接收不同event_id直接拒绝。任务身份本身包含event_id，但容器仍是单事件 |
| 视觉/执行编译 | src/kaiti_task_sim/clinic_visual.py及scripts/run_clinic_visual_execute.py | source绑定、E1编号、依赖、cargo_group及服务反馈路由均有E1专用逻辑，正式执行器不能由本轮离线PASS自动获得多事件能力 |

原异常为有意义的能力门禁，不是一个可以删掉的多事件开关。本轮保留原文件和检查，改在独立模型里为活动监护提供完整、有身份的剩余区间，所以原backend仍能看到完整同事件剩余义务。

## 3. 新的事件与执行状态表示

每个event_index条目含独立event_id、phase、角色任务映射、candidate_at、confirmed_at、复核来源、位置来源和handover_required。候选只释放verify；CONFIRMED/ACTIVE才有完整响应图。终态需要本事件的显式证据，COMPLETED要求verify、monitor、pickup、deliver、handover各自凭据，不能借另一事件完成。

全局MultiEventRegistry按事件复用原状态转移，一个事件只有一个所有者。它在提交前检查机器人全局占用与携货；E1携货owner不能开始E2的无关动作。verify成功还必须有event-bound显式复核，monitor结束还必须有本事件delivery和handover；不实现活动监护或实物携货交接。

导入原实际protocol快照时检查文件SHA、快照内容和视频注册凭据一致；保留原RUNNING状态、owner、execution_target、attempt与execution_revision。原视频行为证据已过TTL，但合格注册位置仍有效，不能因E2到达而把E1当作新事件或自动释放其监护。历史消息去重缓存不包含在业务快照中，未伪造重建该缓存。

## 4. 活动监护的剩余区间模型

真实来源是`bed_before_pickup_04/before_bed.json`：快照241.93秒，E1监护实际在240.57秒由r1开始；r2已派发E1取货导航，r3已派发常态W2。采用这份未阻挡的真实活动状态，而不是把原S2 capability_gate中288.52秒的BED_WAIT状态假装变成可用。

对活动monitor：

- 原实际开始时刻、目标、record task ID、owner和执行token留在active_bindings。
- MILP的s_monitor表示当前快照起的剩余区间起点，固定为now；不再表示重新执行的服务开始。
- 剩余最小时间为max(0, minimum-(now-actual_started_at))；原start deadline在actual_started_at上核对，原finish deadline保持。
- 响应代价采用actual_started_at-confirmed_at作为常数，不能重新计一次响应或用残余区间开始冒充实际开始。
- 活动monitor固定为原机器人的首段；已派发取货导航也固定原owner和goal，没有取消或更换旧指令。

继续保持每个事件监护早于pickup、覆盖deliver+4秒、取送同车相邻、monitor/courier异机、能力/资格域、原依赖与资源。E1监护后的清场任务仍由原monitor机器人直接执行；courier的常态后缀仍须等清场完成。

原backend暂时不支持monitor资源时长，本层用finish变量重建完整占用区间互斥，独立checker仍读取完整语义资源集合。没有在验收模型中丢掉monitor资源。固定锁、blocked资源及实际lease均包含接近/服务/驶离；实际lease需绑定已有holder task。

目标沿用11月18日独立分配契约和权重，扩展为事件响应求和，不归一化、不改权重。原部署目标没有被修改，原运行配置完整保留。开始时限仍360秒，事件结束期限仍1800秒。

所有预测时间均是条件性计划，不是实际完成。未知BED_WAIT、活动非监护服务恢复及非零活动前缀电池账本仍BLOCKED；不得仅延长ready后宣布恢复。

## 5. 单事件一致性与能力实验

正式目录为`capability_formal_03`，独立审计为`capability_audit_02`。不同阶段开发/失败目录保留，不混为独立样本。

| 输入 | 状态 | 可支持的结论 |
|---|---|---|
| A1 真实活动E1，无E2 | PASS | 已运行监护作为残余区间保留，未来同车取送和清场仍满足；没有第二次monitor start |
| A2 活动E1+新E2候选 | PASS | E2只生成核验；E1的活动监护与取送不被覆盖 |
| A3 活动E1+E2阳性分支，要求监护区间有正重叠 | PASS | 两个角色束、两套身份和共享资源可表达；E2是明确离线复核假设 |
| A4 双事件且G1增加120秒已有预约假设 | PASS | 完整资源可用性和跨事件互斥受检查，无视障碍或资源提前使用的变体被拒绝 |
| A5 仅r1有camera，要求两个监护区间重叠 | INFEASIBLE | CBC证明该能力/占用条件无解，没有解锁活动monitor或删第二事件 |
| A6 issued pickup为未知结束BED_WAIT | BLOCKED | 当前活动状态契约不保证解阻，不调用求解器造固定ready结果 |

A3的一个返回方案中：E1仍为r1，actual monitor start=240.57，剩余区间从241.93至434.93，交付预测430.93；E2监护由r3从426.93至642.93，交付预测638.93。二者监护重叠8秒。这里所有未来时间均为计划，E2未实际执行。

0.001秒重叠要求仅是检验同时监护能力的结构约束，不是新增应急响应阈值。E1原第三角色业务约束保持；E2用预先指定常态后缀C0_r1_W3声明离线同类连续性政策，不声称正式部署已有这一多事件政策。

待执行单事件的当前源码对照在`single_pending_smoke_02`：新旧模型均证明最优，目标相等、差0，两份返回方案均通过双方检查。这是该冻结fixture上的最优值与可行见证一致，不是通用形式化等价证明。活动monitor旧模型本来不支持，采用残余区间代数测试和原身份/约束复核，不宣称旧模型曾合法接受它。

负例包括事件ID交换、错误关闭、丢失monitor、跨事件cargo owner、G1重叠、过早释放、旧state_version、改变attempt及issued owner，均通过门禁/独立检查拒绝。UNKNOWN状态单独实现；本轮正式输入没有出现UNKNOWN，不制造一个超时结果凑覆盖。

## 6. S4只读诊断

`s4_diagnosis_01.json`的11项核对通过，分类为**合法的不同表示口径**，不是物资丢失。

原来源为失败/未完成的`bed_before_pickup_01/repair_03/problem.json`，快照438.72秒：

- actual_snapshot.r2.cargo=E1，active_commitment.cargo_at_snapshot=E1，actual job和record task ID均指向r2的E1_deliver。
- 407.47 episode秒的pickup succeeded worker ACK和protocol反馈一致：robot r2、attempt1、task_revision1；协议明确cargo_owner=r2、IN_CUSTODY。
- actual_known_finishes的取货结束为422.42，属于实际任务/清场结束记录，不与407.47的服务ACK混为同一阶段。
- normalized snapshot的job/cargo为None，是bed_contract.project先保存真实states，再对proxy清空job/cargo并移动到后缀source，供dense_tasks.problem使用的结果。原实际状态仍保存，未被proxy覆盖。
- worker feedback的at是ROS时钟，诊断比较episode_time，不直接跨时钟相减。

当前配送活动记录的attempt/sent_revision等字段缺失，保持缺失，不能将取货token拿来填配送token。因此本轮通过的是这次字段差异的原因诊断，不是完整配送token链和未知阻挡恢复已通过。

对未知阻挡只提出条件性计划与滚动观测：每条未来可用时间需写明假设与有效视界，到期重观测、重新验证状态/lease/token；实际可派发必须经过真实路径和依赖ACK门禁。预测到期不等于解阻、完成或cancel ACK，不能提前释放monitor或转交物资。本轮未实施新正式恢复后端。

## 7. LTLf独立验收

旧4条规则与表保持不动；新入口使用8条事件级规则，Spot 2.15.1生成表。复用旧运行时LtlfTraceMonitor，不在ROS环境安装Spot，不引入LTL解析器或新分配器。

事实由真实worker反馈与protocol反馈的event/task/robot/revision/attempt匹配后建立。显式核验来源独立检查；receiver交接读取原受控场景记录。原receiver日志只有event_id与先前delivery绑定，没有独立receiver token，该细粒度范围没有补造。

| 真实历史日志 | 结果 |
|---|---|
| positive_02正例 | PASS_ACTUAL_TRACE_TEMPORAL_SCOPE，10条实际语义事实 |
| bed_before_pickup_04成功床扰动 | PASS_ACTUAL_TRACE_TEMPORAL_SCOPE，10条事实，继承真实计划版本至7 |
| visual_false_alarm_a2误报核验关闭 | PASS_ACTUAL_TRACE_TEMPORAL_SCOPE，3条事实；无阳性响应的规则未触发，单列coverage |
| bed_before_pickup_01失败/未完成运行 | INCONCLUSIVE_PREFIX，6条事实，保留未决监护/配送义务，不伪造成功 |

实际plan_revision直接读取日志或online snapshot；没有版本字段的commit保留“版本未记录”，不自行编号冒充真实版本。checkpoint恢复保留自动机状态、latched facts和活动义务。

控制负例覆盖E1 ACK不能完成E2、跨计划版本释放monitor、错误关闭、提前receiver ACK、截断轨迹、计划预测伪作完成。新双事件数据只有优化计划，全部排除在实际执行LTLf证据之外。
